# Data model reference

The database as it stands on `main` after TAR-19 — every table, which of them are
tenant-scoped, and the constraints that carry meaning. Written for engineers building
against the schema (TAR-20, TAR-21, TAR-22, TAR-35 and everything after them).

This page describes **what shipped**. `apps/api/prisma/schema.prisma` is the source of
truth and carries the per-model reasoning next to each model;
[`docs/architecture/0002-architecture-and-api-contract.md`](../architecture/0002-architecture-and-api-contract.md)
records _why_ the entities are shaped this way. Where the contract and the shipped schema
differ, this page is the one that matches the database.

For how to reach these tables safely, read
[Tenant-scoped data access](../guides/tenant-scoped-data-access.md).

## What landed

Six migrations, applied in this order:

| Migration                                         | What it does                                                              | Story  |
| ------------------------------------------------- | ------------------------------------------------------------------------- | ------ |
| `20260810120000_baseline_extensions`              | `pgcrypto` and `citext`                                                   | TAR-47 |
| `20260810130000_initial_data_model`               | Every table, index and enum                                               | TAR-47 |
| `20260810140000_tenant_isolation_rls`             | `FORCE ROW LEVEL SECURITY` and the `tenant_isolation` policy on 33 tables | TAR-48 |
| `20260810150000_tenant_deactivation_guard`        | `assert_tenant_active(text)`, the deactivation gate                       | TAR-51 |
| `20260810160000_whatsapp_business_account_entity` | Splits WABA out of `whatsapp_accounts`, and protects the new table        | TAR-52 |
| `20260810170000_harden_tenant_deactivation_guard` | Pins the gate's `search_path`; refuses a malformed tenant id as `TN001`   | TAR-51 |

Each directory carries a hand-written `down.sql` next to Prisma's `migration.sql`, per
ADR 0001 decision 6.

Row-level security is only half the mechanism. The other half is
[`apps/api/prisma/sql/app-roles.sql`](../../apps/api/prisma/sql/app-roles.sql), which is not
a migration and must be run once per environment **after** migrations (`pnpm db:roles`).

## Counts, and the three exceptions

**37 tables. 34 are tenant-scoped**: they carry a non-null `tenant_id`, they have
`FORCE ROW LEVEL SECURITY`, and they have the `tenant_isolation` policy. Three are not, each
deliberately:

| Table            | Why it has no policy                                                                                   |
| ---------------- | ------------------------------------------------------------------------------------------------------ |
| `tenants`        | It _is_ the tenant. Provisioning and host→tenant resolution both read it before any tenant is in scope |
| `plans`          | Platform-wide product catalogue — the same rows for every tenant. Public product data, not tenant data |
| `webhook_events` | Written before the tenant is known, so `tenant_id` is nullable and a policy would reject every ingest  |

`TenantPrisma` applies its own rule to all three, because RLS cannot — see
[the guide](../guides/tenant-scoped-data-access.md#the-three-tables-rls-does-not-cover).

`pnpm db:verify:rls` derives the list from the Postgres catalog rather than from a file, so
a table added later without a policy fails the check by name instead of being assumed fine.

## Conventions

Six hold across every model. A change that breaks one needs a reason in review.

1. **Every tenant-scoped table carries a non-null `tenant_id`**, even where the tenant is
   already reachable through a foreign key. Denormalised on purpose: an RLS policy is a row
   predicate and cannot join.
2. **Tenant-scoped foreign keys are composite** — `(tenant_id, <parent_id>)` referencing the
   parent's `UNIQUE (tenant_id, id)`, never the parent's `id` alone. RLS stops a tenant
   _reading_ another tenant's row; this is what stops one being _referenced_ by a handler
   that took an id from a request body. The cost is one extra unique index per referenced
   table, paid deliberately.
3. **Composite indexes lead with `tenant_id`**, so the RLS predicate and an application
   filter use the same access path. Sort keys are `(<timestamp> DESC, id DESC)`.
4. **Referential actions are only ever `Cascade` or `NoAction`.** Never `Restrict`, which is
   checked immediately and would abort a legitimate cascading tenant delete. Never
   `SetNull`, which on a composite key nulls `tenant_id` too — so removing a user is a status
   change (`UserStatus.removed`), not a row delete.
5. **Ids are UUIDv7**, generated by the Prisma client. Postgres 17 has no native `uuidv7()`,
   so there is **no column default** — anything inserting outside the client (a fixture, a
   seed) must supply the id.
6. **Types.** Timestamps are `timestamptz(3)`; money is integer minor units plus an ISO 4217
   code; phone numbers are E.164; emails, slugs and hostnames are `citext`, so `A@b.com` and
   `a@b.com` collide on a unique index rather than becoming two accounts.

## Tables

`tenant_id` is omitted from the constraint column throughout — every scoped table has one.

### Tenancy

| Table             | Scoped | Constraints that carry meaning                                                                |
| ----------------- | ------ | --------------------------------------------------------------------------------------------- |
| `tenants`         | —      | `slug` unique (`citext`); `status`; `trial_ends_at`; `suspended_at`; index on `status`        |
| `tenant_domains`  | ✓      | `hostname` unique **globally** (`citext`); `kind`; `verified_at`; `is_primary`                |
| `tenant_branding` | ✓      | `UNIQUE (tenant_id)` — one row per tenant                                                     |
| `tenant_settings` | ✓      | `UNIQUE (tenant_id)`; `timezone` default `UTC`; `locale` default `en`; `business_hours` JSONB |

`hostname` is unique globally, not per tenant: it is the lookup key on an unauthenticated
request, and two tenants claiming one host has no correct answer.

`tenants.suspended_at` records when deactivation revoked access. There is no `deleted_at`:
deactivation retains data, and deletion is a separate operation TAR-36 owns.

### Identity and access

| Table          | Scoped | Constraints that carry meaning                                                                      |
| -------------- | ------ | --------------------------------------------------------------------------------------------------- |
| `users`        | ✓      | `UNIQUE (tenant_id, email)` on `citext`; `UNIQUE (tenant_id, id)`; `role`; `status`; `availability` |
| `sessions`     | ✓      | `token_hash` unique; `expires_at`; `revoked_at`; index `(tenant_id, user_id)`; index `(expires_at)` |
| `invites`      | ✓      | `token_hash` unique; `expires_at`; `accepted_at`                                                    |
| `teams`        | ✓      | `UNIQUE (tenant_id, name)`; `UNIQUE (tenant_id, id)`                                                |
| `team_members` | ✓      | `UNIQUE (tenant_id, team_id, user_id)`                                                              |

**Identity is tenant-scoped, not global.** Someone who works for two client organisations
gets two accounts with two passwords. Confirmed with Tarek on TAR-39; the migration path if
that ever changes is additive — keep `users` as the membership row, add a global
`identities` table, and join.

Session and invite tokens are stored **hashed**, never in the clear, so a database leak does
not hand over live sessions.

### WhatsApp channel

Meta scopes its objects at three levels, and TAR-52 gives the middle one a table of its own:

```
Tenant ──< whatsapp_business_accounts   waba_id, access token, verification status
              ├──< whatsapp_accounts    phone_number_id, display number, quality rating
              └──< message_templates    name, language, approval status
```

| Table                        | Scoped | Constraints that carry meaning                                                                                              |
| ---------------------------- | ------ | --------------------------------------------------------------------------------------------------------------------------- |
| `whatsapp_business_accounts` | ✓      | `waba_id` unique **globally**; `access_token_encrypted`; `verification_status`; `UNIQUE (tenant_id, id)`                    |
| `whatsapp_accounts`          | ✓      | `phone_number_id` unique **globally**; `whatsapp_business_account_id`; `quality_rating`; `status`; `UNIQUE (tenant_id, id)` |
| `message_templates`          | ✓      | `UNIQUE (tenant_id, whatsapp_business_account_id, name, language)`; `status`; `components` JSONB                            |

**A tenant may hold more than one WABA.** Confirmed with Tarek on TAR-39, question 6. Two
consequences the schema exists to express:

- **The access token belongs to the business, not to the number.** Meta issues it per WABA,
  so it is stored once per WABA and a rotation is a single-row update that cannot leave two
  numbers holding different secrets. It is encrypted at rest, decrypted only in the send
  path, and never selected into an API response.
- **Template approval belongs to the WABA.** One tenant can hold `order_update` / `en`
  approved separately under two WABAs — separate submissions, possibly different content and
  different status. That is why the unique key names the WABA rather than the tenant alone.

Quality rating stays on the phone number, where Meta puts it: Meta rates and throttles each
number separately, so two numbers under one WABA can sit at different ratings. `NULL` means
we have never asked; `unknown` is a value Meta itself returns.

`phone_number_id` remains globally unique because it is the webhook routing key — one Meta
app serves every tenant, so an id arriving on a webhook must resolve to exactly one row.
That does not change with several WABAs behind it.

**Not modelled yet:** messaging limits. Meta's tier vocabulary is version-dependent, and
TAR-20 adds the column once it has confirmed it against Meta's current documentation.

**Migrating from the TAR-47 shape.** `whatsapp_accounts` previously carried a denormalised
`waba_id` and `access_token_encrypted`, and `message_templates` was keyed
`UNIQUE (tenant_id, name, language)`. TAR-52's migration moves both columns and re-keys the
templates. It **aborts if either table holds a single row**: dropping
`access_token_encrypted` would destroy the only copy of a live credential, so a database with
data must go down the expand → backfill → contract path instead.

### Contacts

| Table               | Scoped | Constraints that carry meaning                                                                    |
| ------------------- | ------ | ------------------------------------------------------------------------------------------------- |
| `contacts`          | ✓      | `UNIQUE (tenant_id, phone_e164)`; `UNIQUE (tenant_id, id)`; `custom_fields` JSONB; `opted_out_at` |
| `tags`              | ✓      | `UNIQUE (tenant_id, name)`; `UNIQUE (tenant_id, id)`                                              |
| `contact_tags`      | ✓      | `UNIQUE (tenant_id, contact_id, tag_id)`; index `(tenant_id, tag_id)`                             |
| `custom_field_defs` | ✓      | `UNIQUE (tenant_id, key)`; `type`; `options` JSONB                                                |

`(tenant_id, phone_e164)` is the natural key for an inbound message: every inbound webhook
resolves a contact through it. A non-null `opted_out_at` blocks outbound sends.

### Inbox

| Table                 | Scoped | Constraints that carry meaning                                                                                                                  |
| --------------------- | ------ | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| `conversations`       | ✓      | `UNIQUE (tenant_id, whatsapp_account_id, contact_id)`; `UNIQUE (tenant_id, id)`; `service_window_expires_at`; `last_message_at`; `unread_count` |
| `messages`            | ✓      | `UNIQUE (tenant_id, provider_message_id)`; `UNIQUE (tenant_id, id)`; `direction`; `status`; `sent_at`                                           |
| `message_attachments` | ✓      | `message_id`; re-hosted `url`; `mime_type`                                                                                                      |
| `internal_notes`      | ✓      | `conversation_id`; `mentioned_user_ids uuid[]`                                                                                                  |

One conversation per contact per WhatsApp number. `service_window_expires_at` is Meta's
24-hour customer service window as a column, not a derived value — past it, only an approved
template may be sent.

`messages.provider_message_id` is null until an outbound send is acknowledged, which is why
the unique constraint tolerates it: Postgres does not collide NULLs. Once set, it is what
makes a replayed webhook a no-op. Threads sort by the provider's `sent_at`, never by insert
order — Meta does not guarantee delivery order and ingest is concurrent.

### Tickets, assignment and SLA

| Table              | Scoped | Constraints that carry meaning                                                             |
| ------------------ | ------ | ------------------------------------------------------------------------------------------ |
| `tickets`          | ✓      | `UNIQUE (tenant_id, number)`; `UNIQUE (tenant_id, id)`; `status`; `priority`               |
| `ticket_events`    | ✓      | Append-only; `type` is free text; index `(tenant_id, ticket_id, created_at DESC, id DESC)` |
| `assignment_rules` | ✓      | Evaluated in ascending `position`, first match wins; `conditions` / `action` JSONB         |
| `assignment_state` | ✓      | `UNIQUE (tenant_id, team_id)` — the round-robin cursor, one row per team                   |
| `sla_policies`     | ✓      | `UNIQUE (tenant_id, name)`; `UNIQUE (tenant_id, id)`; `business_hours_only`                |
| `sla_timers`       | ✓      | `UNIQUE (tenant_id, ticket_id, kind)`; index `(tenant_id, state, due_at)`                  |

`tickets.number` is per-tenant and human-facing: two tenants both having ticket #1 is
correct. TAR-21 owns how it is allocated; the unique constraint is what makes a racy
allocator fail loudly instead of duplicating.

`ticket_events.type` is text rather than an enum because every later story adds event types,
and an enum would make each of them a migration.

The SLA sweep index is `(tenant_id, state, due_at)`, **not** the partial index
`(tenant_id, due_at) WHERE state = 'running'` the architecture contract named. Prisma cannot
express a `WHERE` on an index, and an index created outside the schema shows up as drift that
the next `migrate dev` proposes to drop. Leading with `state` gives the sweep the same access
path — equality on `state`, then a range scan on `due_at` — at the cost of also indexing
finished timers. Revisit as a partial index once timer volume makes the size matter; the
query does not have to change.

### Billing

| Table            | Scoped | Constraints that carry meaning                                                          |
| ---------------- | ------ | --------------------------------------------------------------------------------------- |
| `plans`          | —      | `key` unique; `entitlements` JSONB; `price_minor_units` + `currency`                    |
| `subscriptions`  | ✓      | `UNIQUE (tenant_id)`; `provider_subscription_id` unique; index `(provider_customer_id)` |
| `usage_counters` | ✓      | `UNIQUE (tenant_id, metric, period_start)`; `value BigInt`                              |

`usage_counters.value` is `BigInt` because message counts over a long-lived tenant outgrow
`int4`. `period_start` is the subscription's own billing period, never the calendar month, so
a counter can never straddle two invoices when a tenant upgrades mid-month.

### Platform plumbing

| Table              | Scoped   | Constraints that carry meaning                                                  |
| ------------------ | -------- | ------------------------------------------------------------------------------- |
| `webhook_events`   | nullable | `UNIQUE (provider, provider_event_id)`; `status`; index `(status, received_at)` |
| `idempotency_keys` | ✓        | `UNIQUE (tenant_id, key)`; `request_hash`; `expires_at`; index `(expires_at)`   |
| `audit_logs`       | ✓        | Append-only, no `updated_at`; index `(tenant_id, created_at DESC, id DESC)`     |

`UNIQUE (provider, provider_event_id)` is what makes a Meta retry a no-op: the ingest insert
is `ON CONFLICT … DO NOTHING`.

`audit_logs.actor_user_id` is null when the actor is the platform rather than a user inside
the tenant — which is the case for every deactivation. `metadata` holds a redacted
before/after at most: never PII, never a secret value.

## Enums

Native Postgres enums rather than text plus a `CHECK`: a typo becomes an error at write time
instead of a filter that silently matches nothing. Adding a value is cheap
(`ALTER TYPE … ADD VALUE`); removing one is not. Anything genuinely open-ended —
`ticket_events.type`, workflow definitions — stays text or JSON for that reason.

`message_status` is an ordered ladder for outbound messages — `queued` → `sent` →
`delivered` → `read`. `received` is the terminal state of an inbound message and never
advances. TAR-20's `isMessageStatusAdvance` reads that order so a late `sent` webhook cannot
un-read a message.

### Two enums that do not line up, on purpose

`tenant_status` (the column) has four values. `TENANT_STATUSES` in
`packages/contracts/src/tenant.ts` has six — the billing-driven lifecycle a customer sees,
with `trialing`, `past_due` and `deleted`, and no spelling for `pending`.

The drift is known and recorded. The two were authored by different stories against different
concerns, and reconciling them belongs to TAR-36, which owns the lifecycle state machine.
Doing it earlier would mean either an `ALTER TYPE` nobody asked for or a lossy mapper that
reports `pending` as something it is not. `PROVISIONED_TENANT_STATUSES` in
`packages/contracts/src/admin.ts` is the column's vocabulary, used by the admin API;
`contract.test.ts` pins the overlap so the drift cannot widen unnoticed.

## Adding a table

Two steps beyond `pnpm db:migrate`, because Prisma's schema language cannot express
row-level security and nothing generates them:

1. Append the `ENABLE` / `FORCE` / `CREATE POLICY tenant_isolation` block to the generated
   migration, copying an entry from `20260810140000_tenant_isolation_rls`, and the matching
   `DROP POLICY` / `DISABLE` to its `down.sql`.
2. Re-run `pnpm db:roles`, which grants the new table to both roles and gives it its
   `system_unrestricted` policy.

Forgetting either fails `pnpm db:verify:rls` by name, and the two failures are not
equivalent. Skip step 1 and the table has no row-level security at all, so the app role reads
every tenant's rows — a silent isolation hole. Skip step 2 and the table is RLS-protected but
has no `system_unrestricted` policy, so `SystemPrisma` sees nothing on it — fail-closed, and
loud.
