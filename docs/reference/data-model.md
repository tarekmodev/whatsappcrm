# Data model reference

The database as it stands on `main` after TAR-47, TAR-48, TAR-51, TAR-52, TAR-66, TAR-80
and TAR-92. Written for engineers building against it.

`apps/api/prisma/schema.prisma` is the source of truth for columns, types and defaults,
and carries the per-model reasoning next to each model. This document does not transcribe
it — a hand-copied column list drifts the first time somebody adds a field. What it gives
you is what the schema file cannot show at a glance: which tables are tenant-scoped, which
constraints carry meaning, which indexes are load-bearing, and which story owns each
entity.

Read [`docs/architecture/0002-architecture-and-api-contract.md`](../architecture/0002-architecture-and-api-contract.md)
first for _why_ the entities are shaped this way. Read
[`tenancy.md`](tenancy.md) for how the isolation this document classifies is enforced at
runtime.

## Conventions

Six rules hold across every model. A change that breaks one needs a reason in review.

1. **Every tenant-scoped table carries a non-null `tenant_id`**, even where the tenant is
   already reachable through a foreign key. Denormalised on purpose: an RLS policy is a
   row predicate and cannot join.
2. **Tenant-scoped foreign keys are composite** — `(tenant_id, <parent_id>)` referencing
   the parent's `UNIQUE (tenant_id, id)`, never the parent's `id` alone. Row-level
   security stops a tenant _reading_ another tenant's row; the composite key is what stops
   one being _referenced_ by a handler that took an id from a request body.
3. **Composite indexes lead with `tenant_id`**, so an RLS-filtered query and an
   application-filtered query use the same index. Sort keys are
   `(<timestamp> DESC, id DESC)`, which gives keyset pagination a total order.
4. **Referential actions are only ever `Cascade` or `NoAction`.** Never `Restrict`, which
   is checked immediately and would abort a legitimate cascading tenant delete. Never
   `SetNull`, which on a composite key nulls `tenant_id` as well — and that column is
   `NOT NULL`. Removing a user is therefore a status change (`UserStatus.removed`), not a
   row delete.
5. **Ids are UUIDv7**, generated by the Prisma client (`@default(uuid(7))`). PostgreSQL 17
   has no native `uuidv7()`, so there is no column default: anything inserting outside the
   client must supply the id.
6. **Timestamps are `timestamptz(3)`.** Money is integer minor units plus an ISO 4217
   code. Phone numbers are E.164. Emails, slugs and hostnames are `citext`, so `A@b.com`
   and `a@b.com` collide on a unique index instead of becoming two accounts.

## Tenancy classification

37 models. **34 are tenant-scoped**: they carry a non-null `tenant_id`, have
`ENABLE`/`FORCE ROW LEVEL SECURITY`, and one `tenant_isolation` policy each. Three are
not, each deliberately:

| Table            | Why it has no policy                                                                                             | Reachable by                                                                |
| ---------------- | ---------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------- |
| `tenants`        | It _is_ the tenant. Provisioning and host→tenant resolution both read it before any tenant is in scope           | `SystemPrisma` for writes; `TenantPrisma` reads are narrowed to the own row |
| `plans`          | Platform-wide product catalogue, shared by every tenant                                                          | `TenantPrisma` read-only; `SystemPrisma` for writes                         |
| `webhook_events` | Written _before_ the tenant is known — storing first and routing later is the point — so `tenant_id` is nullable | `SystemPrisma` only. The app role is granted nothing on it                  |

`TenantPrisma` applies its own rule to all three, because there is no policy to do it —
see [`tenancy.md`](tenancy.md#the-three-tables-with-no-rls-policy).

Counting these yourself: `pnpm db:verify:rls` reads the catalog rather than a list, so a
table added without a policy is reported by name rather than assumed to be fine.

## Entity reference

Grouped by domain, in the order they appear in `schema.prisma`. Every entity below is
tenant-scoped unless the row says otherwise.

### Tenancy — TAR-19 / TAR-29 / TAR-36

#### `tenants`

One customer business. The root of every cascade in the schema.

- **Tenant-scoped:** no. See the table above.
- **Model:** `Tenant`
- **Unique:** `slug` (`citext`, globally unique)
- **Indexes:** `(status)`
- **Owned by:** TAR-19

`status` is the provisioning-and-lifecycle vocabulary `pending` → `active` → `suspended` →
`cancelled`, and it is the value `assert_tenant_active` reads on every tenant statement.
Only `active` reaches data. `suspended_at` records when access was revoked; there is no
`deleted_at`, because deactivation retains data and is not a delete.

> This is **not** the same vocabulary as `TENANT_STATUSES` in
> `packages/contracts/src/tenant.ts`, which is the billing-driven lifecycle a customer
> sees (`trialing`, `past_due`, `deleted`). The drift is known, pinned by
> `packages/contracts/src/contract.test.ts`, and TAR-36 owns reconciling it.

#### `tenant_domains`

Host → tenant resolution. The first half of tenant resolution on every request.

- **Unique:** `hostname` (`citext`, **globally** unique — an unauthenticated request has
  only the host to go on, so two tenants claiming one host has no correct answer)
- **Indexes:** `(tenant_id)`
- **Relations:** `tenants` → `tenant_domains`, `Cascade`
- **Owned by:** TAR-19, custom domains TAR-29

`kind` is `platform` or `custom`. `verified_at` is null until DNS and TLS check out; an
unverified row must not resolve a request. Provisioning issues the platform subdomain
under our own zone and stamps `verified_at` immediately — there is nothing for the
customer to prove.

#### `tenant_branding`

White-label presentation. One row per tenant, all columns nullable.

- **Unique:** `tenant_id`
- **Owned by:** TAR-29

#### `tenant_settings`

Operational defaults. One row per tenant, written by provisioning.

- **Unique:** `tenant_id`
- **Owned by:** TAR-19

`timezone` is an IANA zone name and drives business hours, SLA calculation and report
bucketing; stored timestamps stay `timestamptz` regardless. `business_hours` is JSON
because its shape is presentation-driven, and TAR-26 owns its interpretation. Feature
stories add columns here rather than inventing a second settings table.

### Identity and access — TAR-22 / TAR-35

#### `users`

The agents of a tenant. Identity is **tenant-scoped**, not global.

- **Unique:** `(tenant_id, email)` on `citext`; `(tenant_id, id)`
- **Indexes:** `(tenant_id, status)`
- **Owned by:** TAR-35

`role` has three values, not four: TAR-80 removed `owner`, which no code ever wrote and
which `TenantRoleSchema` would have rejected at the serializer. Adding a value back is one
online `ALTER TYPE ... ADD VALUE`; removing one is a type swap and a table rewrite, which
is why it was done while `users` and `invites` were empty everywhere.

`last_seen_at` is denormalised from `sessions.last_seen_at` (TAR-80) and is not
`last_login_at`: an agent who logged in on Monday and is working now was last seen now.
Reading it per row would make the people list an aggregate over `sessions`, and sessions
are swept on expiry, so the history would go with them.

Someone who works for two client businesses gets two accounts with two passwords. The
architecture document records the additive migration path — keep `users` as the
tenant-scoped membership row, add a global `identities` table, join — should that turn out
to be wrong. `password_hash` is Argon2id and null for an invited user who has not accepted.

#### `sessions`

Opaque server-side sessions.

- **Unique:** `token_hash` (globally unique)
- **Indexes:** `(tenant_id, user_id)` for bulk revoke on a role change or password reset;
  `(expires_at)` for the cross-tenant expiry sweep
- **Owned by:** TAR-35

The token itself is never stored, only its hash, so a database leak does not hand over
live sessions.

#### `invites`

- **Unique:** `token_hash` (globally unique)
- **Indexes:** `(tenant_id, email)`, `(tenant_id, invited_by_user_id)`
- **Owned by:** TAR-35

#### `teams`, `team_members`

- **Unique:** `teams (tenant_id, name)` on `citext`, `(tenant_id, id)`;
  `team_members (tenant_id, team_id, user_id)`
- **Indexes:** `team_members (tenant_id, user_id, team_id)` — "which teams is this user
  in", answered on every session bootstrap to fill `SessionPrincipal.teamIds`. `team_id`
  trails rather than being absent so the answer comes out of the index without touching the
  heap; it replaces the narrower `(tenant_id, user_id)`, which was a prefix of it
- **Owned by:** TAR-22, aligned to the contract by TAR-80

`teams.name` is `citext` for the same reason every other human-typed unique key is: an
admin creating `billing` beside an existing `Billing` would otherwise get two teams that
look identical in every picker, and conversations routed to one would be invisible to the
members of the other. `description` is nullable text; `TeamCreateInput` caps it at 500
characters, which is the contract's bound to enforce rather than a column type's.

### WhatsApp channel — TAR-20 / TAR-52

Meta scopes its WhatsApp objects at **three** levels, and since TAR-52 so does the schema:

```text
tenants ──< whatsapp_business_accounts       waba_id, access token, verification status
                ├──< whatsapp_accounts        phone_number_id, display number, quality rating
                └──< message_templates        name, language, approval status
```

A tenant may hold several WABAs (WhatsApp Business Accounts), each with one or more phone
numbers. Two consequences follow from Meta's own scoping, and they are the reason the
middle level exists:

- **The access token is issued to the business, not to the number.** One copy per WABA, so
  a rotation is a single-row update that cannot leave two numbers holding different
  secrets.
- **Template approval is per WABA.** One tenant can hold `order_update`/`en` approved
  separately under two WABAs, with different content and different status.

Quality rating and messaging limits stay on the phone number, where Meta puts them.

**What changed in TAR-52.** TAR-47 modelled this against the assumption on the table at
the time — one WABA per tenant — and collapsed the top two levels into a single
`whatsapp_accounts` row carrying a denormalised `waba_id` text column. When TAR-39's open
question 6 was answered as _one or more_ WABAs per tenant, that collapse produced two
defects: `message_templates` keyed `UNIQUE (tenant_id, name, language)` rejected a
legitimate second approval, and the access token sat on the phone-number row where a
rotation is an N-row update whose rows can drift apart. Migration
`20260810160000_whatsapp_business_account_entity` splits the level. It refuses to run
against a database with even one row in `whatsapp_accounts` or `message_templates`,
because it drops `access_token_encrypted` and `waba_id` outright — with data present the
same change has to be redone as expand → backfill → contract.

#### `whatsapp_business_accounts`

One WhatsApp Business Account, as Meta scopes it.

- **Unique:** `waba_id` (**globally** unique — one Meta app serves every tenant, so an id
  arriving on a webhook has to resolve to exactly one row); `(tenant_id, id)`
- **Indexes:** `(tenant_id)`
- **Relations:** `tenants` → this, `Cascade`
- **Owned by:** TAR-52, consumed by TAR-20

`access_token_encrypted` is the single most sensitive column in the schema: the per-business
credential, encrypted at rest, decrypted only in the send path, and never selected into an
API response. `verification_status` is modelled as a lifecycle
(`not_verified`/`pending`/`verified`/`rejected`) rather than transcribed from Meta, which
exposes two different vocabularies here; TAR-20 confirms the mapping against Meta's current
documentation.

#### `whatsapp_accounts`

One phone number, child of a WABA.

- **Unique:** `phone_number_id` (**globally** unique — it is the webhook routing key, and
  that does not change with several WABAs behind it); `(tenant_id, id)`
- **Indexes:** `(tenant_id, whatsapp_business_account_id)`
- **Relations:** `whatsapp_business_accounts` → this on `(tenant_id, whatsapp_business_account_id)`, `Cascade`
- **Owned by:** TAR-52, consumed by TAR-20

`quality_rating` is Meta's per-number rating. NULL means it has never been read; `unknown`
is a value Meta itself returns. The two are not the same thing. Messaging limits are not
modelled yet — Meta's tier vocabulary is version-dependent, and TAR-20 adds the column once
it has confirmed it.

#### `message_templates`

A template belongs to the WABA that submitted it for approval.

- **Unique:** `(tenant_id, whatsapp_business_account_id, name, language)`
- **Indexes:** `(tenant_id, status, name, language, id)` — added by TAR-20a to serve
  `GET /api/v1/message-templates`. The unique index cannot: it leads with the WABA, while
  that list may span a tenant's WABAs, so without this the composer's template picker is a
  sequential scan. `status` sits second because the endpoint filters on exactly one value,
  and a name-leading order is what makes the `q` prefix a range scan
- **Owned by:** TAR-52, consumed by TAR-20 and TAR-66

There is deliberately no separate `(tenant_id, whatsapp_business_account_id)` index: the
unique index leads with exactly those two columns, so "every template in this WABA" already
has an access path, and a second index on the same prefix would cost write throughput and
serve no read.

The key leads with `tenant_id` even though the WABA already implies one, because every
unique index has to lead with `tenant_id` for RLS to use it. `components` stores Meta's
component tree verbatim and is deliberately unvalidated — its shape is Meta's to change.

### Contacts — TAR-33

#### `contacts`

- **Unique:** `(tenant_id, phone_e164)` — the natural key every inbound webhook resolves a
  contact through; `(tenant_id, id)`
- **Indexes:** `(tenant_id, created_at DESC, id DESC)`
- **Owned by:** TAR-33

`custom_fields` is JSONB keyed by `custom_field_defs.key`, so a tenant adding a field is a
row insert rather than a migration. A non-null `opted_out_at` blocks outbound sends.

#### `tags`, `contact_tags`

- **Unique:** `tags (tenant_id, name)`, `(tenant_id, id)`;
  `contact_tags (tenant_id, contact_id, tag_id)`
- **Indexes:** `contact_tags (tenant_id, tag_id)` — "every contact with this tag", the
  filter that makes tags useful
- **Owned by:** TAR-33

#### `custom_field_defs`

- **Unique:** `(tenant_id, key)`
- **Owned by:** TAR-33

### Inbox — TAR-20

#### `conversations`

One thread per contact per WhatsApp number.

- **Unique:** `(tenant_id, whatsapp_account_id, contact_id)`; `(tenant_id, id)`
- **Indexes:**
  - `(tenant_id, status, last_message_at DESC, id DESC)` — the inbox list, the hottest
    query in the product
  - `(tenant_id, assigned_user_id, status, last_message_at DESC, id DESC)` — an agent's
    default view, the `conversation:read` (no `_all`) inbox
  - `(tenant_id, assigned_team_id, status, last_message_at DESC, id DESC)`
  - `(tenant_id, contact_id)`
- **Owned by:** TAR-20, sort keys added by TAR-80

`service_window_expires_at` is Meta's 24-hour customer service window. Past it, only an
approved template may be sent — so it is a stored column, not a derived value.
`last_message_at` and `unread_count` are denormalised from `messages` to keep the inbox
list a single-table scan, and are maintained in the same transaction as the message insert.

**`last_message_at` is `NOT NULL`, defaulting to the row's own insert time** (TAR-92), and
that is load-bearing rather than tidiness: it is the leading sort column of all three inbox
keyset indexes. PostgreSQL orders NULLs first under `DESC`, so a message-less conversation
would pin itself to page one, and the ruled resume predicate evaluates to NULL — not TRUE —
for that cursor, silently dropping every row after it. A thread with no message yet sorts
by when it was opened.

The two assigned-scope indexes carry their sort key rather than stopping at `status`.
Without it the planner drops the scope predicate to a filter and walks the tenant-wide index
instead, so the work scales with the tenant's conversation count rather than with the
principal's. Both are named explicitly with `map:` because Prisma's generated name for five
columns exceeds PostgreSQL's 63-character identifier limit and would be silently truncated.

#### `messages`

- **Unique:** `(tenant_id, provider_message_id)`; `(tenant_id, id)`
- **Indexes:** `(tenant_id, conversation_id, sent_at DESC, id DESC)` — thread view and
  keyset pagination; `(tenant_id, sender_user_id)`
- **Owned by:** TAR-20

`sent_at` is the provider's timestamp and never insert order: Meta does not guarantee
delivery order and ingest is concurrent. `provider_message_id` is null until an outbound
send is acknowledged, which is why the unique constraint tolerates it — PostgreSQL does not
collide NULLs — and once set it is what makes a replayed webhook a no-op. `status` is an
ordered ladder (`queued` → `sent` → `delivered` → `read`) so a late webhook cannot un-read
a message; `received` is the terminal state of an inbound message and never advances.

#### `message_attachments`

- **Indexes:** `(tenant_id, message_id)`
- **Owned by:** TAR-20

`url` is re-hosted by us, because Meta's media URLs expire.

#### `internal_notes`

Agent-only notes on a conversation. Never sent to the contact.

- **Indexes:** `(tenant_id, conversation_id, created_at DESC, id DESC)`,
  `(tenant_id, author_user_id)`
- **Owned by:** TAR-20

`mentioned_user_ids` is a plain `uuid[]` rather than a join table: it is written once, read
with the note, and never queried the other way round.

### Tickets — TAR-21 / TAR-25 / TAR-32

#### `tickets`

- **Unique:** `(tenant_id, number)` — per-tenant, human-facing; two tenants both having
  ticket #1 is correct; `(tenant_id, id)`
- **Indexes:** `(tenant_id, status, priority, created_at DESC)` — ticket queues and
  supervisor dashboards; `(tenant_id, assigned_user_id, status, created_at DESC, id DESC)`
  and `(tenant_id, assigned_team_id, status, created_at DESC, id DESC)` — the
  `ticket:read` (no `_all`) queue, carrying its own sort key for the same reason the inbox
  ones do; `(tenant_id, conversation_id)`, `(tenant_id, contact_id)`
- **Owned by:** TAR-21 / TAR-25, sort keys added by TAR-80

TAR-21 owns how `number` is allocated; the unique constraint is what makes a racy allocator
fail loudly instead of duplicating.

#### `ticket_events`

Append-only audit trail for a single ticket.

- **Indexes:** `(tenant_id, ticket_id, created_at DESC, id DESC)`,
  `(tenant_id, actor_user_id)`
- **Owned by:** TAR-32

`type` is text rather than an enum: every later story adds event types, and an enum would
make each of them a migration. `actor_user_id` is null when the actor is the system.

### Assignment — TAR-23 / TAR-24

#### `assignment_rules`

- **Indexes:** `(tenant_id, is_active, position)`, `(tenant_id, target_user_id)`,
  `(tenant_id, target_team_id)`
- **Owned by:** TAR-24

Rules are evaluated in ascending `position`; the first match wins. `conditions` and
`action` are JSONB, which keeps TAR-24's grammar out of the schema so evolving it is not a
migration.

#### `assignment_state`

Round-robin cursor, one row per team.

- **Unique:** `team_id` (globally); `(tenant_id, team_id)`
- **Indexes:** `(tenant_id, last_assigned_user_id)`
- **Owned by:** TAR-23

### SLA — TAR-26

#### `sla_policies`

- **Unique:** `(tenant_id, name)`; `(tenant_id, id)`
- **Indexes:** `(tenant_id, is_active, priority)`
- **Owned by:** TAR-26

`priority` null means "any". `business_hours_only` counts elapsed time against
`tenant_settings.business_hours` rather than wall-clock.

#### `sla_timers`

- **Unique:** `(tenant_id, ticket_id, kind)` — one timer per target per ticket
- **Indexes:** `(tenant_id, state, due_at)`
- **Owned by:** TAR-26

The architecture document specifies a partial index `(tenant_id, due_at) WHERE state =
'running'` for the timer sweep. Prisma cannot express a `WHERE` on an index, and an index
created outside the schema shows up as drift that the next `migrate dev` proposes to drop.
Leading with `state` gives the sweep the same access path — equality on `state`, then a
range scan on `due_at` in index order — at the cost of also indexing finished timers.
Revisit once timer volume makes the size matter; the query does not have to change.

### Workflows — TAR-27

#### `workflows`, `workflow_runs`

- **Unique:** `workflows (tenant_id, name)`, `(tenant_id, id)`
- **Indexes:** `workflows (tenant_id, is_active)`;
  `workflow_runs (tenant_id, workflow_id, created_at DESC, id DESC)`,
  `(tenant_id, status)`
- **Owned by:** TAR-27

`definition` and `trigger` are JSONB; TAR-27 owns the grammar.

### AI — TAR-28

#### `ai_configs`

- **Unique:** `tenant_id`
- **Owned by:** TAR-28

`handoff_keywords` are phrases that force an immediate handover to a human agent.

#### `knowledge_documents`

- **Indexes:** `(tenant_id, status)`
- **Owned by:** TAR-28

There is deliberately no embedding column. Whether that is `pgvector`, an external index or
nothing at all is TAR-28's decision, and adding the column here would make it look settled.

### Canned responses — TAR-31

#### `canned_responses`

- **Unique:** `(tenant_id, shortcut)`
- **Indexes:** `(tenant_id, created_by_user_id)`
- **Owned by:** TAR-31

### Billing — TAR-37

#### `plans`

- **Tenant-scoped:** no. Platform-wide product catalogue; every tenant chooses from the
  same one.
- **Unique:** `key`
- **Owned by:** TAR-37

`price_minor_units` is an integer count of the currency's minor unit, never a float.
`entitlements` is JSONB so adding an entitlement is a data change rather than a migration.

#### `subscriptions`

One per tenant.

- **Unique:** `tenant_id`; `provider_subscription_id`
- **Indexes:** `(provider_customer_id)` — billing-webhook routing, provider customer id →
  tenant; `(plan_id)`
- **Owned by:** TAR-37

`provider_*` ids are opaque strings only the billing adapter interprets.

#### `usage_counters`

- **Unique:** `(tenant_id, metric, period_start)`
- **Owned by:** TAR-37

`value` is `BigInt`: message counts over a long-lived tenant outgrow `int4`. Incremented
inside the transaction that writes the source row, so a rolled-back webhook replay rolls the
count back with it. `period_start` is the subscription's own billing period, never the
calendar month, so a counter cannot straddle two invoices when a tenant upgrades mid-month.

### Platform plumbing — TAR-20 / TAR-22 / TAR-37

#### `webhook_events`

- **Tenant-scoped:** no, and it is the deliberate exception. Written before the tenant is
  known, so `tenant_id` is nullable and no policy could apply. Written only by
  `SystemPrisma`, from the ingest controller and the sweeper, and never read by
  tenant-facing code. `tenant_id` is filled in during processing, for forensics.
- **Unique:** `(provider, provider_event_id)` — what makes a Meta retry a no-op, since the
  ingest insert is `ON CONFLICT ... DO NOTHING`
- **Indexes:** `(status, received_at)` — the sweeper, which turns a Redis outage into
  lateness rather than loss; `(tenant_id)`
- **Owned by:** TAR-20

#### `idempotency_keys`

Replay protection for unsafe POSTs that cause external side effects. Rows expire after 24
hours.

- **Unique:** `(tenant_id, key)`
- **Indexes:** `(expires_at)` — the cross-tenant expiry sweep
- **Owned by:** TAR-20

`request_hash` is a hash of the request body. A replay with a _different_ body is a client
bug and must answer `409 idempotency_key_reused` rather than return someone else's response.

#### `audit_logs`

Append-only: no `updated_at`.

- **Indexes:** `(tenant_id, created_at DESC, id DESC)`, `(tenant_id, actor_user_id)`,
  `(tenant_id, target_type, target_id)`
- **Owned by:** TAR-22

`actor_user_id` is null when the actor is the platform rather than a user in this tenant —
which is the case for every entry tenant deactivation writes. `metadata` is never PII and
never a secret value; a redacted before/after at most.

## Enums

24 native PostgreSQL enums rather than text plus a `CHECK`. They are the closed sets in the
contract, and a typo becomes an error at write time instead of a filter that silently
matches nothing. The trade-off is that adding a value is cheap (`ALTER TYPE ... ADD VALUE`)
and removing one is not, so anything genuinely open-ended — `ticket_events.type`, workflow
definitions — stays text or JSON.

| `tenant_status`                         | `pending`, `active`, `suspended`, `cancelled`                                                                                |
| `tenant_domain_kind`                    | `platform`, `custom`                                                                                                         |
| `user_role`                             | `admin`, `supervisor`, `agent` — `owner` removed by TAR-80; it is exactly `TENANT_ROLES` in `packages/contracts/src/rbac.ts` |

| `whatsapp_quality_rating`               | `green`, `yellow`, `red`, `unknown`                                                                                          |

### Adding a table

Two steps that no generator produces, because Prisma's schema language cannot express
row-level security:

1. Append the `ENABLE` / `FORCE` / `CREATE POLICY tenant_isolation` block to the migration,
   copying an entry from `20260810140000_tenant_isolation_rls`, and the matching
   `DROP POLICY` / `DISABLE` to its `down.sql`.
2. Re-run `pnpm db:roles`, which grants the new table to both roles and gives it its
   `system_unrestricted` policy.

Forgetting either fails `pnpm db:verify:rls` by name. A tenant-scoped table without a policy
looks finished in review and returns every tenant's rows at runtime.

### Adding a function

Re-run `pnpm db:roles` for that too. `apps/api/prisma/sql/app-roles.sql` names each
function, revokes the default `EXECUTE TO PUBLIC` and grants it to the two application
roles, so a routine `REVOKE EXECUTE ... FROM PUBLIC` hardening step is survivable rather than
an outage. Schema-qualify the call site (`public.my_function(...)`) and pin the function's own
`SET search_path`, as `20260810170000_harden_tenant_deactivation_guard` does.

### One trap worth knowing

**`@default(now())` is generated by the client, not the database.** Prisma 7 fills the value
in and sends it, so the `DEFAULT CURRENT_TIMESTAMP` in the DDL never fires and the timestamp
is the API process's clock at insert time rather than transaction start. It does not matter
for a single row. It does when two rows written together have to agree — read one `now()`
from the database and pass it to both, as `TenantDeactivationService` does for
`suspended_at` and its audit entry.
