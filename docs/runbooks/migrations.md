# Migrations

Prisma is the migration tool (ADR 0001, decision 6). Migrations are applied
**automatically at deploy time** and every one of them is **reversible**.

## How a migration reaches an environment

Nobody applies a migration by hand.

`render.yaml` gives each API service a pre-deploy hook:

```
preDeployCommand: pnpm --filter @whatsappcrm/api db:deploy   # prisma migrate deploy
```

Render runs it after the build and **before** the new instance starts serving. So:

1. The build produces the image the migration and the application both run from —
   schema version and code version cannot drift apart.
2. A failing migration aborts the deploy. The previous instance keeps serving.
3. Development deploys on every commit, staging when CI is green, production only
   when someone promotes it — so a migration is exercised twice before it reaches
   real tenant data.

`prisma migrate deploy` is idempotent: it applies only what is missing and exits
`0` when there is nothing to do, including on a database with no migrations at all.

## Writing one

Against a local database (docker-compose, TAR-42):

```bash
pnpm --filter @whatsappcrm/api db:migrate --name add_conversation_status
```

That creates the migration **and** its `down.sql`. It wraps `prisma migrate dev`,
which is **local only** — never run it against a deployed database.

Read the generated `down.sql` before committing, then commit both files together.

## Reversibility: the down.sql convention

Prisma does not generate down migrations as part of its workflow. TAR-34 requires
migrations to be reversible, so every migration directory carries a `down.sql`
beside Prisma's `migration.sql`:

```
apps/api/prisma/migrations/
  20260810120000_add_conversation_status/
    migration.sql   generated by Prisma      — applied by `migrate deploy`
    down.sql        generated by db:migrate  — applied by `db:rollback`
```

`pnpm --filter @whatsappcrm/api db:check-migrations` fails when one is missing or
empty, and CI runs it on every pull request. There is no way to merge a migration
that cannot be undone.

### Generating the down SQL

`db:migrate` does this for you. If you ever need to do it by hand, the **order is
the whole trick**:

```bash
# BEFORE applying anything — new datamodel back to what the database still is:
pnpm --filter @whatsappcrm/api exec prisma migrate diff \
  --from-schema-datamodel prisma/schema.prisma \
  --to-schema-datasource prisma/schema.prisma \
  --script > down.sql

pnpm --filter @whatsappcrm/api exec prisma migrate dev --name <name>
mv down.sql apps/api/prisma/migrations/<the new directory>/down.sql
```

Run that diff _after_ `migrate dev` and both sides are already in sync: it emits
`-- This is an empty migration.`, which passes the CI check and reverses nothing.
That failure is silent, which is exactly why `db:migrate` exists.

**Read what it emits before committing it.** The generator will happily produce a
`DROP TABLE`; that is correct for undoing a release, and catastrophic if it is
run against a table a later migration started depending on. Review it like code.

### Rolling one back

```bash
pnpm --filter @whatsappcrm/api db:rollback            # prints the plan, changes nothing
pnpm --filter @whatsappcrm/api db:rollback --confirm  # runs it
```

It undoes the **single most recently applied** migration: it takes a Postgres
advisory lock, runs that migration's `down.sql`, and deletes its row from
`_prisma_migrations` so `migrate deploy` will apply it again. Repeat the command
to go back further — deliberately, one release at a time.

`DATABASE_URL` decides which database is affected, so export it explicitly and
read it back before adding `--confirm`.

## Rules that make the above safe

These are not style preferences. Environments sit at different schema versions and
a deploy can fail halfway.

- **Additive only within a release.** Add tables, columns, indexes and constraints.
  Do not rename, drop, retype or narrow in the same release that ships code
  depending on the change.
- **Expand and contract across releases.** A rename is: add the new column, write
  both, backfill, move reads, drop the old one in a much later release.
- **New columns are nullable or have a default.** Making one `NOT NULL` is three
  migrations — add nullable, backfill in batches, then enforce.
- **Guard the DDL.** `IF NOT EXISTS` / `IF EXISTS`, so re-running over a partly
  migrated database succeeds quietly instead of erroring.
- **Never edit an applied migration.** Corrections ship forward as a new one.
- **One logical change per file.** It also means two branches never edit the same
  file, so migrations do not produce merge conflicts.
- **Create indexes concurrently** on large tables, and run heavy backfills as a
  separate batched job rather than inside the migration.

## Before you merge

Check the migration applies:

- to a brand-new database,
- to a database one version behind,
- twice in a row (it must be a no-op the second time),

and that `db:rollback --confirm` followed by `db:deploy` returns the schema to
where it started.
